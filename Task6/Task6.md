# Проектирование движка классификации данных

Задача состоит во внедрении движка классификации данных в рамках озера данных.
Решение разрабатывается с соблюдением принципа Privacy by Design.

## Цель

Ввести классификацию данных до загрузки в аналитическое хранилище с тем чтобы:

- выявлять персональные, медицинские данные и другую чувствительную информацию;
- ввести основания для контроля доступа на основе политик безопасности;
- предотвратить утечку данных и нарушение требований законодательства;
- поддержать гибкость структуры входных данных в ожидании её изменения;
- подготовить данные к обработке в BI, ML и AI-системах.

## C2-диаграмма

[Диаграмма](c2.plantuml)

### 1. Landing Zone (приёмный слой)

- Хранит сырые данные в неизменном виде;
- Формат хранения: столбцовое хранилище (Parquet/ORC) + метаданные (schema, source, timestamp);
- Доступ только у ETL-процессов и аудита;
- Шифрование: симметричное, at-rest (AES-256).

### 2. Data Classification Engine (движок классификации)

**Вход**:

- Сырые данные;
- Динамическая схема;
- Метаданные источника.

**Выход**:

- Размеченные данные с тегами конфиденциальности;
- Журнал классификации (audit log);
- Отчёт о качестве и покрытии.

**Компоненты движка**:

| Подсистема                   | Описание                                                                                                                          |
|------------------------------|-----------------------------------------------------------------------------------------------------------------------------------|
| Schema Discovery & Inference | Автоматически определяет типы данных, имена колонок, шаблоны (например, email, phone, ИНН). Реализация: Apache Spark + Deequ.     |
| Pattern Matching             | Находит известные шаблоны PII/PHI (используются регулярные выражения, словари).                                                   |
| NLP + ML Classifier          | Модель на основе распознавания естественных языков для распознавания содержания. Обучается на аннотированных медицинских текстах. |
| Metadata Enricher            | Добавляет теги к колонкам.                                                                                                        |
| Policy Engine                | Применяет политики безопасности. Например, если колонка имеет тэг `PII`, то запрещено попадание в Gold-слой без анонимизации.     |
| Anonymization Gateway        | При необходимости применяет: маскирование, псевдонимизацию, генерализацию (например, возраст → диапазон).                         |

### 3. Data Lake

| Слой       | Назначение                                                    | Доступ                                 |
|------------|---------------------------------------------------------------|----------------------------------------|
| Бронзовый  | Сырые данные + теги классификации                             | Только ETL, администраторы             |
| Серебряный | Очищенные данные, но с конфиденциальной информацией (PII/PHI) | Только доверенные роли (врачи, юристы) |
| Золотой    | Агрегированные, анонимизированные данные                      | Все аналитики, BI, ML                  |


Меры безопасности:
    - Шифрование в покое и в движении (TLS 1.3, KMS).
    - Разделение ролей (RBAC + ABAC), например:
        - Врач видит PHI, но только по своим пациентам.
        - Аналитик видит только Gold, без PII.
        - Ресепшен видит только текущие записи, без истории.
    - Аудит доступа через ELK / Victoria Metrics + Alerting.
    - Тегирование данных в каталоге.
    - Автоматическое удаление по запросу клиента.

Метрики эффективности классификации

| Метрика                  | Формула / Описание                              | Зачем нужна                                                   |
|--------------------------|-------------------------------------------------|---------------------------------------------------------------|
| Точность                 | TP / (TP + FP)                                  | Минимизировать ложные срабатывания (например, "Иван" как ФИО) |
| Полнота                  | TP / (TP + FN)                                  | Не пропустить реальные PII (например, скрытый email)          |
| F1-score                 | 2 × (Precision × Recall) / (Precision + Recall) | Баланс между точностью и полнотой                             |
| Покрытие данных          | % колонок с тегами / общее число колонок        | Оценка качества инвентаризации                                |
| Скорость обработки       | строк/секунда                                   | Для масштабирования                                           |
| Число инцидентов доступа | Кол-во попыток доступа к запрещённым данным     | Оценка эффективности контроля                                 |

## Масштабируемость

1) Горизонтальное масштабирование ETL: Apache Spark на Kubernetes.
2) Serverless обработка классификации: функции (например, Yandex Cloud Functions) для легковесных проверок.
3) Очереди сообщений: Kafka.
4) Dynamic Scaling: автоматическое увеличение ресурсов при росте объёмов (HPA в Kubernetes).
